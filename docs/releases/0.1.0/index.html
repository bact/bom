This document defines the Baseline-information Obligations Mapping ontology, a bridging vocabulary of stable, persistent identifiers for the minimum elements required in a Bill of Materials (BOM) and regulatory compliance standards.

This document is a draft version of the Baseline-information Obligations Mapping ontology v0.1.0, developed to support crosswalk mappings between information requirement specs and exchange formats.

Introduction & Architecture

The BOM Ontology bridges the gap between various regulatory obligations, information requirement specifications, and technical serialization formats (such as SPDX and CycloneDX).

It functions in four distinct layers:

  • Layer A: Information Requirement Specs — baseline requirements (e.g. NTIA, CISA, FSCT, G7 AI, BSI, MOF).
  • Layer B: Tiered Assessment Frameworks — maturity level models.
  • Layer C: Regulatory Specs — legally binding regulations (e.g. EU AI Act).
  • Layer D: The Bridge Ontology — the canonical concept scheme (bom:) acting as a pivot for all mappings.

Rather than mapping $N \times M$ combinations of formats and specifications directly, all specifications are mapped via a "one-hop" alignment: Source Concept → Bridge Concept → Exchange Format Field.

Core Classes & Properties

The ontology defines type classes to categorize specifications and properties to model constraints and normative provisions:

Term Type Description
bom:InfoRequirementSpec owl:Class A standard or guidance document specifying which baseline information MUST/SHOULD be present.
bom:RegulatorySpec owl:Class A legally binding instrument that mandates compliance-related obligations (e.g. EU AI Act).
bom:ExchangeFormatSpec owl:Class A technical specification defining a serialization format for compliance document content.
bom:valueConstraint owl:ObjectProperty Links a concept to a SKOS Collection of allowed values for the mapped field.
bom:provisionType owl:ObjectProperty The normative strength of a requirement element (SHALL, SHOULD, etc.) linking to the provision type vocabulary.

Provision Type Vocabulary

Normative requirements are categorized into six provision types aligned with ISO/IEC Directives Part 2 §7 and RFC 2119:

Concept Keywords Definition
bom:Requirement SHALL, MUST, REQUIRED Mandatory; absence makes the document non-conformant with the source specification.
bom:ConditionalRequirement SHALL IF, MUST IF Mandatory when specific conditions hold (e.g. if the data exists).
bom:Recommendation SHOULD, RECOMMENDED Highly recommended; valid reasons may exist to omit the element, but consequences must be understood.
bom:Permission MAY, OPTIONAL Completely optional; absence has no conformance implication.
bom:PossibilityAndCapability CAN Statement of technical possibility or capability rather than a requirement.
bom:ExternalConstraint MUST (External) Mandatory due to external legal requirements or regulations outside the requirement specification.

Bridge Concepts

The neutral bridge concepts are grouped under seven top-level categories:

Document Metadata (bom:bom-document)

Concept Preferred Label Definition
bom:doc-author Document Author The entity (person, organization, or tool) that created the document.
bom:doc-timestamp Document Timestamp The timestamp indicating when the document data was compiled.
bom:doc-identifier Document Identifier A unique identifier (URI or serial number) for the document.
bom:doc-relationship Document Relationship Defines metadata relationships between the document and its contained elements.
bom:doc-comment Document Comment General comments or remarks concerning the document itself.

Component Attributes (bom:bom-component)

Concept Preferred Label Definition
bom:component-supplier Component Supplier The entity that supplies the component (which might differ from the original developer/author).
bom:component-name Component Name The name of the software component as designated by its creator.
bom:component-version Component Version The version identifier of the component.
bom:component-identifier Component Identifier Unique identifiers such as CPE, SWID, or Package URL (PURL).
bom:component-relationship Component Relationship Dependency, nesting, or compilation relationships between software components.
bom:component-hash Component Hash Cryptographic checksum (SHA-512, etc.) verifying component integrity.
bom:component-license Component License Concluded, declared, or effective licenses associated with the component.
bom:component-external-ref Component External Reference Pointers to external pages, security policies, or vulnerability disclosure locations.
bom:component-documentation Component Documentation Technical reports, research papers, manuals, or configuration files describing the component.

Software-Specific Attributes (bom:bom-sw)

Concept Preferred Label Definition
bom:is-executable Component Executable Property A flag indicating whether the component is executable (e.g. executable vs library/script).
bom:is-archive Component Archive Property A flag indicating whether the component is an archive or distribution bundle.
bom:is-structured Component Structured Property A flag indicating whether the component file has structured metadata present.
bom:component-source-code Component Source Code Source code files or packages for training, inference, evaluation, or data pre-processing.

AI-Specific Attributes (bom:bom-ai)

Concept Preferred Label Definition
bom:ai-application-domain AI Application Domain The domain (e.g. healthcare, finance) where the AI model is intended to be used.
bom:ai-data-flow AI Data Flow Description of inputs, outputs, and information pipelines through the AI system.
bom:ai-data-usage AI Data Usage Normative limits or conditions on data processed during model inference.
bom:ai-io-prop AI IO Properties Input and output formats, modalities, and interface properties of the model.
bom:ai-model-prop AI Model Properties AI model architectural properties (model type, explainability, safety characteristics).
bom:ai-training-prop AI Training Properties Hyperparameters, fine-tuning configuration, and hardware resource footprint.
bom:ai-model-card AI Model Card A structured document (model card) covering model details, intended uses, evaluation factors, risks and mitigations.
bom:ai-model-parameters AI Model Parameters The trained weights, biases, checkpoints, and optimizer state of the AI model.
bom:ai-perf-metric Performance Metric Model performance metrics (adversarial robustness, accuracy thresholds).

Dataset Attributes (bom:bom-dataset)

Concept Preferred Label Definition
bom:dataset-type Dataset Type Modality or types of content inside the dataset (image, text, tabular).
bom:dataset-provenance Dataset Provenance Information about collection, preprocessing, and chain of custody.
bom:dataset-statistical-prop Dataset Statistical Properties Noise levels, class distributions, and bias assessments.
bom:dataset-sensitivity Dataset Sensitivity Presence of sensitive/personal information and anonymization status.
bom:dataset-data-card Dataset Data Card A structured document (data card) providing summary statistics and details about training datasets, features, instances, and intended uses.

Infrastructure Attributes (bom:bom-infra)

Concept Preferred Label Definition
bom:infra-software Infrastructure Software The software stack (frameworks, runtimes, container images, OS) supporting operation.
bom:infra-hardware Infrastructure Hardware Hardware host requirements, including specialized computing accelerators (GPUs, TPUs).

Security Attributes (bom:bom-security)

Concept Preferred Label Definition
bom:security-controls Security Controls References to security safeguards, access controls, or encryption methods in place.
bom:security-compliance Security Compliance Compliance with standards or frameworks (ISO/IEC 42001, NIST AI RMF).
bom:security-policy Security Policy Vulnerability disclosure guidelines, contact information, or security.txt.
bom:security-vuln-ref Vulnerability Reference Known CVEs and VEX assessments linked to the components.
